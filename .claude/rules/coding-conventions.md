# Unity C# 코딩 컨벤션

## 1. 기본 원칙
- 새로운 패턴을 도입하기보다 가독성, 작은 변경, 인접 코드와의 일관성을 우선한다.
- 단순 기능을 위해 내부 클래스, `sealed` 클래스, 불필요한 인터페이스, 범용 프레임워크 또는 계층을 추가하지 않는다.
- Unity 직렬화나 Inspector 연동이 실제로 필요하지 않은 일시적 런타임 로직은 순수 C# 클래스를 우선 검토한다.
- 매직 넘버를 피하고 수치·시간 값은 의미 있는 상수 또는 명시적인 설정으로 관리한다.

## 2. 네이밍
- 타입, 공개 멤버, 메서드: `PascalCase`
- 매개변수, 지역 변수: `camelCase`
- 비공개 필드: `_camelCase` (기존 코드에 다른 일관된 규칙이 있으면 해당 규칙을 우선 확인)
- `moveSpeed`, `attackCooldownSeconds`처럼 의미가 드러나는 이름을 사용하고 모호한 축약어를 피한다.

## 3. 구현 규칙
- 가능한 범위에서 클래스와 메서드의 책임을 명확하게 분리한다.
- 깊은 중첩보다 조기 반환(early return)을 우선한다.
- 기존 공개 API와 직렬화 필드명을 보존한다. 직렬화 필드명 변경은 Scene/Prefab 연결을 깨뜨릴 수 있다.
- `Update()`처럼 자주 호출되는 경로에서 불필요한 할당이나 비용이 큰 조회를 피한다.
- 이벤트 구독은 수명 주기에 맞춰 해제한다.
- 주석은 모든 코드를 설명하기보다 설계 의도, 불변 조건, 이해하기 어려운 타이밍 로직에 작성한다.

## 4. 검증
- 컴파일 오류, null 처리, 경계 조건을 확인한다.
- 저장소의 기존 테스트 구성과 호환되고 실효성이 있을 때 테스트를 추가한다.
- 실제로 실행하고 확인하지 않은 Unity 컴파일이나 빌드를 성공했다고 보고하지 않는다.
