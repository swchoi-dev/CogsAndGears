# Git 브랜치 및 커밋 정책

> **브랜치 생성, Commit, Push, PR, Merge는 개발자가 직접 수행한다.** Claude Code는 이 정책을 기준으로 브랜치명·커밋 메시지·PR 본문을 제안하고, 변경 사항을 읽기 전용으로 점검한다. 명시적 요청과 승인 없이는 Git 쓰기 작업을 하지 않는다(`cg-role-boundary.md`).

## 1. 브랜치 역할
| 브랜치 | 역할 |
| --- | --- |
| `prod` | 운영·릴리스 기준 브랜치. WebGL 배포 기준(7장). `develop`에서 PR로만 반영 |
| `develop` | 기능 통합 및 검증. 기능 브랜치에서 PR로 병합 |
| `feature/<Issue 번호>-<기능명>` | GitHub Issue 단위 기능 개발 브랜치. **`develop`에서 분기** |

- `main` 등 위 표에 없는 기존 브랜치는 개발자가 처리 방침을 정하기 전까지 변경·삭제를 제안하지 않는다.
- `develop`, `prod` 브랜치 생성과 GitHub 기본 브랜치 변경은 개발자가 수행한다.

## 2. 필수 흐름
```text
develop
   └── feature/12-cogs-movement
           └── PR → develop (통합 검증)
                       └── PR → prod (릴리스)
```
- 기능 브랜치는 원칙적으로 최신 `develop`에서 생성한다. `prod`에서 분기하지 않는다.
- 기능 구현 및 로컬 검증 후 `develop`으로 PR을 생성한다.
- 릴리스 시 `develop` → `prod` PR로 병합한다. 기능 브랜치를 `prod`에 직접 병합하지 않는다.
- `prod`에 직접 개발 내용을 커밋하지 않는다.
- CI 빌드 성공 여부는 실제 CI 실행 결과로만 판단한다.

## 3. 기능 브랜치명
- 형식: `feature/<GitHub Issue 번호>-<영문 소문자 kebab-case 기능명>`
- 예: Issue `#12 Cogs 좌우 이동` → `feature/12-cogs-movement`
- Issue 번호는 `gh issue view <번호>`로 실제 존재를 확인한 값만 사용한다. 확인할 수 없으면 임의로 만들지 않고 확인을 요청한다.
- 기능명은 Issue 제목의 의미를 보존하는 짧은 영문 slug로 만든다. 공백·특수문자는 `-`로 정리한다.
- 기존 브랜치의 이름 변경이나 중복 생성을 제안하지 않는다.

## 4. 커밋 가이드
- `[feat]`: 기능 추가, 변경, 삭제 등 개발 전반
- `[fix]`: 개발 진행 중 **Bug Issue** 관련 수정
- `[docs]`: 문서 작업
- `[chore]`: 코드 컨벤션 맞춤 및 기타 작업

**형식:** `[type] 변경 내용 요약`

예:
```text
[feat] Cogs 좌우 이동 구현
[fix] 카메라 추적 떨림 수정
[docs] 연금술 가방 인벤토리 설계 문서 추가
[chore] Player 스크립트 네이밍 정리
```
- 유형은 실제 Issue 유형과 변경 목적에 따라 선택한다.
- Issue 연결: 작업 중간 커밋은 본문에 `Refs #번호`, Issue를 완료하는 커밋은 `Closes #번호`를 쓴다. 단, `Closes`는 기본 브랜치에 병합될 때 Issue를 자동으로 닫으므로 완료 조건 검증 전이면 `Refs`를 사용한다.
- 관련 파일만 커밋한다. Unity `.meta` 파일과 GUID를 보존한다.
- 캐시·빌드 산출물(`Library/`, `Temp/`, `Logs/`, 빌드 결과물)·비밀 정보는 커밋하지 않는다.

### 4.1 커밋 단위
커밋은 파일·폴더·클래스 단위가 아니라 **논리적으로 완결된 변경 단위**로 만든다. 목표는 커밋 수를 줄이는 것이 아니라 목적과 책임에 맞게 묶는 것이다.

- 같은 목적을 달성하는 연관 변경은 하나의 커밋으로 묶는다. 파일이나 폴더가 다르다는 이유만으로 나누지 않는다.
- 하나의 Issue가 반드시 여러 커밋일 필요는 없다.
- 기능 구현과 해당 기능의 테스트·설정 변경은 함께 커밋할 수 있다.
- 독립적으로 검토하거나 되돌려야 하는 변경은 별도 커밋으로 분리한다.
- 중간 작업 상태를 기록하기 위한 커밋은 만들지 않는다.
- 커밋 수를 줄이려고 서로 무관한 변경을 억지로 합치지 않는다.

**분리 판단:** 분리할 이유가 명확하지 않으면 하나로 묶는 것이 기본값이다.
- 두 변경이 같은 목적을 달성하는가?
- 하나만 독립적으로 되돌릴 필요가 있는가?
- 분리하면 리뷰가 실질적으로 쉬워지는가?
- 분리된 커밋이 각각 의미 있는 완결 상태인가?

## 5. PR 정책
- 기능 PR: `feature/<번호>-<기능명>` → `develop`
- 릴리스 PR: `develop` → `prod`
- PR 본문에 Issue, 변경사항, 주요 파일, 검증 결과, 미검증 항목, 위험/리뷰 포인트를 기재한다.
- PR 생성과 병합은 개발자가 수행한다. Claude Code는 요청 시 PR 제목·본문 초안만 작성한다.

### 5.1 PR 제목
PR 제목은 Merge commit 제목으로 그대로 사용된다(5.2). 개별 커밋 메시지(4장)와 역할을 구분한다.

| PR | 형식 | 예 |
| --- | --- | --- |
| 기능 → `develop` | `Merge: #<Issue 번호> 작업명` | `Merge: #12 Cogs 좌우 이동` |
| `develop` → `prod` | `Release: 릴리스 내용` | `Release: 프로토타입 1차 WebGL 배포` |

- PR 번호는 제목에 쓰지 않는다. GitHub가 Merge commit 제목에 자동으로 붙인다.

### 5.2 Merge commit
- 병합 전략은 **Create a merge commit**을 유지한다. Squash merge, Rebase merge로 바꾸지 않는다.
- GitHub 저장소 설정 `Allow merge commits → Default to pull request title`을 전제로, PR 제목이 Merge commit 제목이 된다.

## 6. 안전
- 작업 트리의 미커밋 변경을 임의로 삭제·덮어쓰기·stash하지 않는다.
- 강제 Push, `git reset --hard`, `git clean`, 브랜치 삭제, merge/rebase를 수행하지 않는다.
- PR 생성만으로 Issue를 완료 처리하지 않는다.

## 7. 배포 정책
> 현재 단계에서는 배포 파이프라인을 구현하지 않는다. 아래는 정책이며, 파이프라인 도입은 별도 Issue로 진행한다.

| 대상 | 기준 브랜치 | 방식 |
| --- | --- | --- |
| WebGL | `prod` | 향후 GitHub Actions로 빌드·배포 자동화 예정 |
| Windows | `prod` | 개발자가 직접 빌드. 자동 빌드·배포 도입하지 않음 |

- `develop`과 `feature/*`에서는 운영용 WebGL을 배포하지 않는다.
- 배포 설정(빌드 설정, GitHub Actions 워크플로, 배포 대상)은 승인 없이 변경하지 않는다.
