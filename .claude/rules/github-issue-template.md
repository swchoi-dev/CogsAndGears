# GitHub Issue 작성 템플릿

> GitHub Issue의 제목·본문 **작성 형식**만 정의한다. 생성·수정 시점과 승인 절차는 `github-issue-workflow.md`를 따른다.
## 1. 적용 대상
- 상위·하위 Issue 생성
- 기존 Issue 본문 수정, 범위 변경 반영

기존 Issue를 수정할 때는 본문을 일괄 삭제·재작성하지 않는다. 누락 섹션을 보완하고 변경된 부분만 고친다.

## 2. 하위 Issue 템플릿
```markdown
## 배경 / 목적
- (작업이 필요한 이유)

## 작업 범위
### 포함
- (구현 또는 작성할 내용)
### 제외
- (이번 Issue에서 다루지 않는 내용)

## 완료 조건
- [ ] (검증 가능한 조건)
- [ ] Unity Editor에서 컴파일 오류 및 관련 Error / Warning 로그가 발생하지 않는다.

## 기술 학습 키워드
- (구현에 필요한 Unity API·개념. 예: `Rigidbody2D.linearVelocity`, `InputAction`)

## 참고 문서
- (관련 기획·기술문서, 상위 Issue, 외부 레퍼런스)

## 특이사항
- (해당 시에만 작성)
```

## 3. 상위 Issue 템플릿
```markdown
## 배경 / 목적
- (시스템이 필요한 이유)

## 목표 (To-be)
- (시스템 완성 후 기대 동작)

## 하위 작업
- Sub-issues로 연결한다. (본문에 목록을 중복 작성하지 않는다.)

## 완료 조건
- [ ] 모든 하위 Issue 완료
- [ ] (시스템 단위 통합 검증 조건)

## 참고 문서
- (관련 기획·설계 문서)
```

## 4. 작성 규칙

### 4.1 제목
- 20자 내외의 **기능 단위**로 작성하고 불필요한 수식어를 뺀다.
- Issue 번호나 브랜치명을 제목에 넣지 않는다.
- 예: `Cogs 좌우 이동`, `마우스 360° 조준`, `연금술 가방 격자 배치`

### 4.2 배경 / 목적 (필수)
- 생성 전 사용자에게 배경과 목적을 확인한다. 현재 대화에서 명확히 제공된 정보는 재사용할 수 있다.
- **배경과 목적을 확인할 수 없으면 Issue를 생성하지 않는다.** 추측으로 채우지 않는다.

### 4.3 작업 범위
- 실제 프로젝트 구조를 확인한 뒤 파일 경로를 쓴다. 확인하지 못한 경로는 `(예상)`을 붙인다.
- 새 파일 경로는 `Assets/CogsAndGears/` 아래 기존 폴더 구조(`Scripts/Player`, `Scripts/Combat` 등)를 따른다.

### 4.4 완료 조건
- 실제로 검증할 수 있는 조건만 쓴다. Play Mode에서 관찰 가능한 동작으로 쓴다(예: "`A`/`D` 입력 시 Cogs가 좌우로 이동한다").
- Unity 컴파일·Console 확인 항목을 포함한다.
- 검증하지 않은 항목은 체크(`[x]`)하지 않는다.

### 4.5 기술 학습 키워드
- 개발자가 직접 구현하며 학습할 Unity API, C# 기능, 설계 개념을 3~6개 정도 쓴다.
- 키워드만 나열하고 상세 설명은 기술문서로 넘긴다.

### 4.6 참고 문서
- 존재를 확인한 문서·Issue만 링크한다. 실제 조회한 Issue 번호만 `#번호`로 참조한다.

### 4.7 특이사항 (조건부)
선행 작업, 연관 Issue, 해결된 블로커가 있을 때만 작성한다.

## 5. 검증 기록 댓글 형식
`record-verification` 스킬에서 사용한다.
```markdown
## 검증 기록 (YYYY-MM-DD)

**구현 내용**
- (개발자가 구현한 내용 요약)

**변경 파일**
- `경로` (생성 | 수정 | 삭제)

**검증 결과**
| 완료 조건 | 결과 | 근거 |
|---|---|---|
| (조건) | 통과 / 실패 / 미검증 | 개발자 확인 / 코드 읽기 전용 확인 / PR #N |

**미완료·후속 작업**
- (없으면 "없음")
```
