# 기술문서 작성

> 문서는 저장소 `docs/`에 Markdown으로 관리한다. 문서 작성은 기능 구현이 아니므로 구현 브리핑을 적용하지 않지만, 대상 파일 확인과 Issue 쓰기 승인 절차는 유지한다.

## 문서 위치
| 경로 | 내용 |
|---|---|
| `docs/design/` | 기획·설계 문서 |
| `docs/tech/NN-<제목>.md` | 기능별 기술문서 |
| `docs/learning/keywords.md` | 기술 학습 키워드 목록 |
| `docs/roadmap.md` | 개발 로드맵 |

폴더가 없으면 생성 전에 사용자에게 확인한다.

## 실행 조건
- 기능 개발 완료 후에는 **먼저** 묻는다: "이번 기능을 기술문서에 새로 작성하거나 기존 문서에 반영할까요? 문서화 Issue도 연결할까요?"
- 사용자가 초안만 요청하면 초안을 대화로 제시한다. 파일 작성은 대상 경로를 확인받은 뒤 수행한다.
- 커밋·Push는 개발자가 수행한다.

## 자료 수집
1. 관련 GitHub Issue의 요구사항, 완료 조건, 검증 기록을 조회한다(`gh issue view <번호> --comments`).
2. 관련 코드, 주요 클래스·컴포넌트, 이벤트 흐름을 **읽기 전용**으로 확인한다.
3. 기존 `docs/` 문서 중 해당 영역 문서를 확인해 갱신과 신규 작성 중 무엇이 맞는지 판단하고 대상 파일을 확인받는다.

## 파일명 규칙 (`docs/tech/`)
- 형식: `NN-<영문 kebab-case 제목>.md`, 문서 첫 줄 제목은 `# NN. 한국어 제목`
- **신규:** `docs/tech/`의 실제 파일 목록에서 `NN` 최댓값 + 1을 쓰고 중복이 없는지 확인한다.
- **갱신:** 기존 번호와 파일명을 유지한다. 다른 문서 번호를 바꾸지 않는다.

## 작성 원칙
- 설계 의도, 구성 요소(컴포넌트·이벤트), 데이터 흐름, 제약·예외 처리를 중심으로 짧게 쓴다.
- 다른 문서나 규칙에 있는 내용은 반복하지 않고 링크한다.
- 실제 코드와 개발자가 확인한 검증 결과에만 근거한다. 확인하지 않은 동작은 "미검증"으로 표시한다.
- 문서 끝에 관련 Issue(`#번호`), 검증 상태, 변경 이력을 둔다.
- 새로 등장한 기술 키워드는 `docs/learning/keywords.md`에 추가할지 함께 제안한다.

## 마무리
1. 작성·갱신한 파일 경로와 요약을 보고한다.
2. 문서화 Issue 생성·댓글 연결은 **별도 승인된 경우에만** 수행한다(`github-issue-workflow.md`).
3. 개발 Issue의 close는 이 스킬에서 하지 않는다.
