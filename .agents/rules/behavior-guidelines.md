# 행동·승인·검증

- 실제 파일·요구사항·관련 문서를 확인하고 변경한다. 가정·확인된 사실·개발자 보고·미검증을 구별한다.
- 승인된 작업을 구체적이고 검토 가능한 결과까지 진행한다. 관련 없는 정리·기능·의존성·정책을 추가하지 않는다.
- 외부 쓰기 전 대상과 최종 초안 또는 diff를 준비한다. 기존 대화의 승인이 그 내용을 포함하면 재사용하고, 범위가 바뀌면 변경분을 확인한다. 계획·조회·초안 작성은 쓰기 승인을 뜻하지 않는다.
- 현재 사용자의 작업 제한이 일반 워크플로보다 우선한다. Issue 생성이 금지된 문서 작업을 Issue 등록 때문에 멈추지 않는다.
- 한 작업의 실패로 다른 작업을 우회 실행하지 않는다. 조회 실패는 추정으로 채우지 않고, 독립적으로 가능한 로컬 작업을 계속한다.
- 파일 변경 후 범위·경로·참조·형식을 검증한다. 문서 변경 때문에 Unity를 실행하지 않는다.
- 실행하지 않은 Play Mode·빌드·CI를 통과로 기록하지 않는다. 최종 보고에 변경 파일, 검증 결과, 남은 한계를 명시한다.

## 실행 수준과 조사 범위

분석보다 실행, 반복 조사보다 기존 결과 재사용, 장시간 무응답보다 진행 공유를 우선한다. 이 원칙은 역할 제한과 사용자 승인 범위를 확대하지 않는다.

| 수준 | 판단 기준 | 실행 방식 |
|---|---|---|
| QUICK | Markdown 일부·Issue 제목/본문·우선순위·라벨/일정 등 단순 변경 | 필요한 자료만 확인하고 별도 설계 브리핑 없이 승인 범위에서 즉시 실행한 뒤 결과를 보고한다. |
| STANDARD | 여러 Issue·로드맵·요구사항 매핑·여러 문서 갱신 | 시작 시 3~5줄 실행 계획을 보고하고, 기존 자료를 활용해 작은 단위로 실행·저장·검증한다. |
| DEEP | 전체 아키텍처 재설계·계획 대규모 변경·시스템 간 의존성 재구성 | 조사 범위와 설계 쟁점을 명시하고 중간 산출물을 저장한다. 주요 설계 결정은 사용자 승인 후 실행하되 이미 확정·승인된 결정은 재승인받지 않는다. |

- 길거나 파일이 많다는 이유만으로 DEEP으로 분류하지 않는다.
- 기존 PDF 분석·Issue 초안·구현 조사 결과를 우선 재사용한다. 사용자 확정 사항은 재검토·재질문하지 않고 변경 요구사항에 직접 관련된 부분만 확인한다.
- 추가 조사는 기존 자료의 오류·누락·충돌이 확인된 경우에만 이유와 범위를 밝히고 수행한다. 원본 PDF 전체 재분석, Issue 전체 재작성, 코드베이스 전체 재조사를 기본 절차로 삼지 않는다.

## 진행 보고와 결과 저장

- STANDARD·DEEP은 시작, 주요 단위 완료, 예상보다 복잡해진 시점, 사용자 결정·승인 필요 시점, 완료 시 보고한다. 실행 중에는 가능한 한 60초를 넘겨 무응답 상태가 지속되지 않도록 한다.
- 보고에는 완료한 작업, 실제 생성·수정한 결과물, 현재 단계, 남은 작업, 장애·지연 원인을 간결하게 담는다. 변경이 없으면 조사만 수행했으며 저장된 변경은 없다고 명시한다.
- 메시지를 보낼 수 없는 실행 상태에서는 가능한 첫 응답 시점에 상태를 알린다. 실시간 보고를 보장한다고 표현하지 않는다.
- 각 실행 단위가 끝나면 승인된 로컬 결과를 즉시 저장한다. 모든 분석·검증 후 마지막에 일괄 저장하는 방식은 지양하며, 중단되어도 완료 단위의 결과가 남도록 한다. 저장은 Git stage·Commit·외부 게시를 의미하지 않는다.
- 파일 간 정합성 때문에 원자적 변경이 필요하면 이유와 묶을 범위를 밝히고 함께 저장한다. 외부 쓰기 승인 전에는 로컬 초안까지만 저장한다.

## 정체 감지와 검증 범위

- 같은 자료·조사 결과를 반복 확인하거나 실행 대신 계획만 반복하거나 예상 작업량이 크게 증가하면 즉시 방식을 재검토한다. 산출물 없이 조사 도구 호출이 5회 이어지면 정체 점검 기준으로 삼는다. 안전·정확성에 필요한 검증 호출을 기계적으로 차단하지 않는다.
- 정체 시 확인한 내용과 저장 여부를 요약하고, 즉시 실행 가능한 최소 작업을 선정해 수행·저장한 뒤 나머지를 이어가거나 장애를 보고한다. 승인이 필요한 작업은 실행하지 않고 구체적인 결과와 승인 요청을 준비하며 독립적으로 가능한 작업을 계속한다.
- 검증은 변경 대상과 직접 관련된 부분으로 제한한다. Markdown은 내용·참조 링크, Issue는 개수·제목·URL·하위 관계, 일정은 일정표·관련 Issue 날짜를 확인한다.
- 게임 코드·Unity 파일을 변경하지 않은 작업에서 전체 Unity 파일 해시 검사를 반복하지 않는다. Git 상태는 시작 시 필수 확인 이후 필요할 때 읽기 전용으로 확인한다.
