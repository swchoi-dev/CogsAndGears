# Issue 작성 규칙

초안은 다음 템플릿의 필요한 항목만 재사용하고 아래 작성 기준을 우선한다. 공통 템플릿 전체를 모든 Issue에 복사하지 않는다.
- 하위 작업: [issue-task.md](../templates/issue-task.md)
- 상위 시스템: [issue-epic.md](../templates/issue-epic.md)
- 검증 댓글: [verification.md](../templates/verification.md)

제목은 짧은 기능 단위로 작성하고 Issue 번호·브랜치명을 넣지 않는다. 배경과 목적은 대화·관련 자료의 사실을 사용하며 모르면 확인한다. 경로는 실제 확인하거나 `(예상)`을 붙인다. 참고 링크는 존재를 확인한 문서·Issue만 쓴다.

완료 조건은 관찰·검증 가능해야 한다. Unity 구현 작업은 개발자의 컴파일·Console·Play Mode 확인을 포함한다. 순수 문서·Harness 작업에 Unity 검증 항목을 기계적으로 추가하지 않는다. 미검증 항목은 체크하지 않는다. 기술 학습 키워드는 관련 API·개념 중심으로 작성한다.

## 공통 정책과 Issue 본문 분리

프로젝트 공통 정책, 전체 일정, 우선순위 기준, 아키텍처 원칙은 `AGENTS.md`, 관련 Rules와 승인된 중앙 기획 문서에서 관리한다. 개별 GitHub Issue에는 해당 작업과 직접 관련된 요구사항, 구현 범위, 완료조건만 작성한다.

- 전체 P0~P3 설명, 등록 당시 일회성 지시, 무관한 층수·공격 타입·라이선스 정책을 본문에 일괄 삽입하지 않는다. 해당 작업에 필요한 정책만 구체적인 요구사항으로 남긴다.
- 상위는 시스템·기능 그룹 단위로 `배경 / 목적`, `목표`, `작업 범위`, `하위 작업`, `완료조건`을 작성한다. 실제 Sub-issues는 유지하고 본문에는 필요한 번호·제목 목록만 제시한다. 관계 설정 절차를 반복 설명하지 않는다.
- 하위는 독립적으로 구현·검증 가능한 작업 단위로 `배경 / 목적`, `작업 내용`, `완료조건`을 작성한다. 필요한 설계·알고리즘 입출력·수동 검증·선행 작업·출처는 해당 작업 내용에 간결하게 포함한다.
- 완료조건은 실제 입력·관찰 결과·경계/실패 상황을 명시한다. “기능 완성”, “정상 동작 확인”, “위 공통 검증 기준 충족”만 반복하지 않는다. 상위도 시스템별로 구체적인 검증 조건을 갖춘다.
- GitHub에서 접근 가능한 URL만 Markdown 링크로 쓴다. 로컬 전용 문서는 실제 저장소 경로를 확인한 경우에만 참고 경로로 표시하며, 불필요한 로컬 경로·존재하지 않는 원격 URL을 넣지 않는다. 같은 참고 링크를 모든 Issue에 의무적으로 반복하지 않는다.
- 기존 초안·고유 요구사항·알고리즘·완료조건·수동 검증을 재사용한다. 공통 블록을 제거한다는 이유로 필수 기능을 삭제하지 않는다. 기존 추적표 연결과 계획 ID·실제 Issue 매핑을 보존한다.

기존 본문은 필요한 부분만 보완한다. 승인된 본문 정리는 원문을 백업한 뒤 위 기준으로 구조를 정리할 수 있으나 고유 요구사항과 검증 기준을 보존해야 한다. 게시와 수정은 [github-issue-workflow.md](github-issue-workflow.md)의 승인 범위를 따른다.
