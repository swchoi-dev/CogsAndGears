# GitHub Issues 관리

- 대상은 `swchoi-dev/CogsAndGears`. `gh` 조회에는 `--repo swchoi-dev/CogsAndGears`를 지정한다. 외부 쓰기가 금지된 작업은 초안까지 수행한다.
- 번호가 있으면 조회한다. 없으면 닫힌 항목을 포함해 중복 검색한다. 후보가 여러 개면 대상만 확인한다. 조회 실패 시 내용을 추측하거나 중복 Issue를 생성하지 않는다.
- 신규 생성, 본문·댓글·라벨·마일스톤·Sub-issue·상태 변경은 구체적인 내용에 대한 승인 범위에서만 수행한다. 쓰기 후 재조회하여 실제 번호·URL·반영 내용을 보고한다.
- 상위는 시스템 단위 `type:epic`, 하위는 독립 개발·검증 단위 `type:task|bug|docs`. 하위는 GitHub Sub-issues로 연결하고 영역은 `area:*`로 구별한다. 없는 라벨 생성과 연결 작업도 쓰기 승인 범위에 포함되어야 한다.
- 일반 대화·읽기 전용 분석은 Issue 불필요. 작업 요청은 Issue 초안을 준비하되 등록 승인이 없으면 로컬 결과를 제공한다. 정식 Markdown 작업지시서 원문 보관이 요청되면 `docs/work-orders/issue-{실제번호}-{작업명}.md`에 보관한다. 원격에 없는 문서 링크를 게시하지 않는다.

## 진행
1. Issue·관련 설계·기술문서와 실제 파일을 읽기 전용으로 확인한다.
2. [implementation-brief.md](../templates/implementation-brief.md)로 구현 가이드를 작성한다. 예상 파일은 예상으로 표기한다.
3. 승인된 Issue 보완만 수행한다. 기존 본문 전체를 덮어쓰지 않는다.
4. 개발자가 Unity 기능을 구현한다. Git 관리는 [git-workflow.md](git-workflow.md)에 따라 별도로 승인된 작업만 수행한다.
5. 개발자 동작 검증과 코드 정적 확인을 구별해 기록한다. 실제 근거가 있는 완료 조건만 체크한다.
6. 완료 조건 전체 검증, 개발자 검수, 관련 PR의 `develop` 병합, 기술문서 갱신 또는 불필요 확인을 점검한다. PR이 불필요한 기록 작업은 그 사유를 확인한다. 미검증이 남으면 close하지 않는다. close는 별도 승인 범위에 포함된 경우만 수행한다.

도입 전 완료 작업은 개발자가 확인한 사실과 해당 분류를 명시한다. 예정 작업은 열린 상태와 미체크 완료 조건으로 둔다. `CG-xx` 그룹을 실제 Issue 번호로 변환하지 않는다.
