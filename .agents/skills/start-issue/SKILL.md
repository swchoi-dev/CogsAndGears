# Issue 기반 작업 시작

[역할 제한](../../rules/cg-role-boundary.md), [공통 실행·보고 원칙](../../rules/behavior-guidelines.md), [Issue 절차](../../rules/github-issue-workflow.md), [작성 규칙](../../rules/github-issue-template.md)을 읽는다.

1. 대화에서 Issue 번호 또는 작업 요청을 확인한다. 번호가 있으면 `gh issue view <번호> --repo swchoi-dev/CogsAndGears --json number,title,body,state,labels,url`로 조회한다. 없으면 `gh issue list --repo swchoi-dev/CogsAndGears --state all --search <키워드>`로 중복을 찾는다. 여러 후보의 대상만 확인한다.
2. 기존 계획·초안·생성 기록과 승인 범위를 먼저 확인하고 아래 실행 흐름을 선택한다. 구현 가이드에 필요한 경우에만 관련 문서·상위 Issue·코드·Scene·Prefab의 해당 부분을 읽기 전용 조사한다. Git 시작 상태는 공통 규칙대로 확인하고 기준 브랜치 존재는 브랜치 제안에 필요할 때만 확인한다. 조회 실패는 알리고 추정 Issue를 만들지 않는다.
3. 새 구현 가이드가 필요한 경우 [구현 가이드](../../templates/implementation-brief.md)를 작성한다. 범위·예상 파일·컴포넌트와 이벤트 설계·완료 조건·학습 키워드·위험·브랜치명 제안·Issue 반영 예정 내용을 포함한다. 기존 가이드가 있으면 변경분만 반영한다. 단순 수정·승인된 등록에 가이드 재작성을 요구하지 않는다. 분할이 필요하면 하위 작업 초안을 준비한다.
4. 신규 Issue는 [하위](../../templates/issue-task.md) 또는 [상위](../../templates/issue-epic.md) 초안을 사용한다. 외부 쓰기 금지나 계획만 요청된 작업이면 초안 결과로 마친다.
5. 반영이 승인된 경우만 생성·수정하고 재조회한다. 본문은 임시 파일에 실제 줄바꿈으로 저장해 `--body-file`로 전달한다. 기존 승인 범위를 넘어 라벨·연결·브랜치 작업을 추가하지 않는다.

실제 확인한 Issue 번호·URL, 조사 근거, 가이드, 반영 여부와 남은 질문을 보고한다. 게임 구현과 Git 쓰기를 이 스킬의 부수 작업으로 실행하지 않는다.

## 계획·승인 상태에 따른 실행

- 기존 계획 없음: 필요한 요구사항 분석 → Issue 초안 저장 → 사용자 승인 → GitHub 등록.
- 기존 계획 있음: 기존 계획 확인 → 변경 사항만 반영·저장 → 변경분 사용자 승인 → GitHub 등록. 전체 프로젝트나 원본 PDF를 다시 분석하지 않는다.
- 이미 생성·본문 수정 승인됨: 대상·내용·라벨·연결 등 기존 승인 범위를 확인하고 필요한 중복·동시 변경 확인 후 즉시 실행한다. 승인된 초안과 실행 기록을 재사용하고 전체 계획·기술문서를 다시 작성하지 않는다.
- 외부 쓰기 금지 또는 초안만 요청됨: 로컬 결과로 완료한다. Issue 생성과 전체 기술문서 재작성은 별도 요청 없이 결합하지 않는다.

## 대량 등록·본문 정리 품질 확인

- 실제 연결된 대표 상위1개·하위1개의 본문을 [작성 규칙](../../rules/github-issue-template.md)으로 확인하고, 변경 전후와 사용자 승인 범위를 확정한다. 같은 범위의 기존 승인은 다시 요청하지 않는다.
- 일괄 전송 전에 각 본문에 무관한 공통 정책 블록·의미 없는 동일 문구가 없고 작업 내용·완료조건이 고유한지 확인한다. 전송용 래퍼에서 중앙 정책 전체를 각 본문 앞뒤에 자동 삽입하지 않는다.
- 기존 본문 정리는 최신 본문·번호·제목·상태·관계를 먼저 백업해 복구 가능하게 한다. 고유 범위·알고리즘·완료조건·수동 검증·추적 연결을 보존하고 승인된 본문 필드만 갱신한다. 해석할 수 없는 형식이나 백업 이후 동시 변경은 덮어쓰지 않고 해당 항목을 보고한다.
- 일괄 실행 후 실제 대표 상위·하위 본문을 표본 확인하고 결과 개수·제목/상태·관계를 대조한다. 전체 PDF·코드베이스 재분석이나 게임 테스트로 검증 범위를 확대하지 않는다.

## 실행 기록과 재시도

- 등록·본문 수정은 작은 단위로 수행하고 성공할 때마다 실제 번호·제목·URL·계획 항목 매핑과 성공 여부를 승인된 로컬 계획/기록 파일에 저장한다. 새 파일이 필요하면 허용된 문서 경로에 최소 기록을 남긴다. 하위 관계는 승인된 연결만 수행하고 실제 반영을 확인한다.
- 부분 실패는 성공·실패·미시도 항목과 실패한 연결을 구분해 기록한다. 재시도는 성공 기록을 재사용하고 실패·미시도 항목만 대상으로 한다.
- 생성 응답 유실 등 성공 여부가 불명확하면 서버 상태를 재조회하여 기존 항목을 식별한다. 식별할 수 없으면 해당 항목의 재생성을 멈추고 장애를 보고한다. 중복 위험이 없는 독립 작업은 계속한다.
- 완료 시 생성 개수, 번호·URL, 연결 결과와 남은 실패를 간결하게 보고한다.
